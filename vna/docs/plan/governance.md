# 开发计划治理规则（Governance）

## 1. 执行总则

- 契约先于实现：先定 proto/header/schema，再写实现。
- 测试先于合并：每个任务至少单测；跨模块改动必须含集成测试。
- 小任务闭环：每个任务必须有 DoD。
- 文档同步更新：架构、UI、计划文档与代码同次更新。
- 失败可恢复：关键能力支持开关、降级、回滚。
- Pre-GA 不保兼容：优先删旧用新，避免兼容负担。

## 2. 本机环境约束

- 新增可执行目标必须输出为 `easy_*`（`.exe` 需以 `easy` 开头）。

## 3. AI 角色职责

| 角色 | 主要输出 | 约束 |
|------|----------|------|
| 架构 Agent | ADR、接口边界、风险评审 | 不直接改业务实现 |
| 合约 Agent | proto/schema/header | 兼容性策略受阶段约束 |
| 实现 Agent | core/service/drivers/plugins/apps | 必带测试 |
| 测试 Agent | 单测/集成/E2E/基准 | 不改业务逻辑 |
| 文档 Agent | 设计文档、迁移指南、运行手册 | 与代码版本一致 |

## 4. Work Unit 模板

```markdown
WU-<ID>: <Title>
- Objective:
- Scope (in/out):
- Files to change:
- Contract impact:
- Test plan:
- Rollback plan:
- Risks:
- Acceptance criteria:
```

建议每个 WU 在 1~3 天内闭环。

## 5. WU 收尾要求

1. 更新 `vna/development-plan.md` 中对应 WU 的状态与验证结果。
2. 完成对应提交（默认一个 WU 一个 commit，轻量可批量）。
3. 在交付说明中给出 commit hash 与测试结果摘要。

## 6. 质量门禁

### CI 门禁

1. build：编译通过
2. test：单测 + 集成测试
3. docs-check：接口/架构变更必须有文档更新

### 合并门禁

- 至少 1 个 reviewer（人或受控 Agent）
- PR 必须附测试证据与风险说明
- 禁止无测试功能提交

## 7. 里程碑 DoD

| 里程碑 | 验收标准 |
|--------|----------|
| M0 | Mock + 合约稳定；前端可联调 |
| M1 | Core 稳定；覆盖率达标；关键错误可恢复 |
| M2 | 服务可部署；集成测试通过 |
| M3A | Qt 闭环可用；核心交互延迟可接受 |
| M3B | VS Code 闭环可用；脚本化可执行 |
| M4 | 发布物可安装、可运行、可回滚 |

## 8. 风险与缓解

| 风险 | 影响 | 缓解策略 |
|------|------|----------|
| 硬件能力不达预期 | 阻塞高级功能 | 抽象驱动 + 能力探测 + 降级路径 |
| 多板卡同步不稳定 | 测量误差 | 触发链验证 + 监测 + 延迟补偿 |
| Agent 输出漂移 | 质量不一致 | 执行仓库规范 + PR 模板 |
| 长任务性能不足 | 用户体验差 | 并行调度 + 流式缓冲 + 可取消机制 |
